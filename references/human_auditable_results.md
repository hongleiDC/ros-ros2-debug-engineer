# Human Auditable ROS Noetic Results

## Goal

The final result must remain usable when the AI agent is unavailable. A ROS engineer must be able to inspect saved evidence, rerun the plotting code, reproduce the analysis inputs, and judge the conclusion from project-local artifacts.

## Result structure

Use one directory per actual run:

```text
RUN-xxxx/
├── manifest.yaml
├── metrics.json
├── series/
├── plots/
├── logs/
├── bags/
├── report.md
└── report/
    ├── index.html
    └── analysis_summary.json
```

Use `scripts/result_bundle.py init` to create it. `manifest.yaml` records git/environment/input provenance and a `ros_evidence` section that links native ROS artifacts.

## Native ROS evidence

Prefer ROS Noetic-native sources for runtime evidence:

```text
rosnode / rostopic / rosservice / rosparam
roswtf
rosbag1
ROS launch/node logs under ROS_LOG_DIR or ~/.ros/log
```

Use `scripts/ros_noetic_run_logger.py`:

```bash
python3 scripts/ros_noetic_run_logger.py snapshot RUN_DIR --roswtf
python3 scripts/ros_noetic_run_logger.py record RUN_DIR --topic /result/topic
python3 scripts/ros_noetic_run_logger.py copy-logs RUN_DIR
```

The logger registers produced snapshot/log/bag paths in `RUN_DIR/manifest.yaml` when the directory is a Result Bundle.

Default bag audit topics are `/rosout`, `/rosout_agg`, `/diagnostics`, `/tf`, `/tf_static`, and `/clock`; add project result/input topics explicitly. Do not default to `rosbag record -a` on bandwidth-heavy robots unless the user intentionally wants a full capture.

## ROS-native instrumentation contract

When the existing project does not expose enough evidence, add the smallest useful instrumentation instead of inventing a parallel logging framework:

- use `ROS_DEBUG/ROS_INFO/ROS_WARN/ROS_ERROR/ROS_FATAL` (or rospy logging) for discrete events, mode changes, rejected measurements and failures; these remain visible through rosconsole/`/rosout` and ROS log files;
- use `diagnostic_msgs/DiagnosticArray` / `diagnostic_updater` for health, status, rates and thresholded subsystem conditions;
- publish typed ROS topics for numeric time series that must be plotted or replayed later, including a meaningful `header.stamp` and `frame_id` where applicable;
- record those topics with rosbag1 rather than printing high-rate numeric samples to text logs;
- keep parameter/configuration snapshots and calibration provenance beside the run so a graph can be interpreted later.

Do not duplicate the same high-rate signal into rosconsole text, CSV and bag during runtime without a clear need. Prefer ROS topic + rosbag1 as the raw record, then derive compact CSV/metrics offline.

## Storage contract

Do not use text logs as a replacement for numeric data.

```text
bags/*.bag     high-rate ROS messages and replayable runtime data
series/*.csv   normalized continuous analysis signals
metrics.json   scalar metrics and decision values
logs/          commands, stdout/stderr, roslaunch/node logs, snapshots
plots/         deterministic offline figures
report/        static human-readable review material
```

For algorithm diagnostics, prefer publishing meaningful ROS messages during the run and recording them with rosbag1. Convert only the required analysis signals to stable CSV after the run.

## Project-local visualization

Common localization/SLAM plots are generated by bundled scripts. For arbitrary numeric CSV series use:

```bash
python3 scripts/plot_series.py RUN_DIR/series/diagnostics.csv \
  --x distance_m \
  --y frame_runtime_ms \
  --output RUN_DIR/plots/runtime.png \
  --title "Runtime vs distance" \
  --ylabel ms
```

The plot helper writes a JSON sidecar containing the source file, selected columns, row counts and output path.

Every plot must answer a review question, for example: Did trajectory error increase? Did prediction fail before correction? Did matching lose support? Did runtime exceed the budget?

## Adapter contract

When a project does not expose data in the bundled format, write a small project-local adapter instead of keeping a one-off transformation inside chat. Place reusable code under `tools/analysis/` and require:

- command-line input and output paths;
- explicit source topic/file and column/field mapping;
- documented unit, frame, sign/direction and time semantics;
- deterministic output into `series/`, `plots/` or `logs/`;
- no dependency on an AI session, database or hidden service;
- a minimal requirements file when extra Python packages are required.

For visualization adapters, save the plotting source alongside the project so the user can regenerate figures later. For logging adapters, prefer ROS publishers + rosbag1 for high-rate structured data and ROS logging/diagnostics for events and state changes.

## Human review workflow

```text
ROS run
→ native ROS snapshot + rosbag1 + roslaunch logs
→ normalized series + metrics
→ deterministic plotting code
→ static HTML report
→ human review / decision
```

Generate the static report with:

```bash
python3 tools/analysis/analyze_run.py RUN_DIR --strict
python3 tools/analysis/result_bundle.py validate RUN_DIR --closure --human-analysis
```

If native ROS runtime evidence is part of the acceptance requirement, add `--ros-audit`.

`ready_for_human_review: true` only means the required evidence and report are present. It does not mean the algorithm is correct or should be deployed.

## Reproducibility minimum

Save git commit/dirty state, launch/YAML configuration, relevant bag hashes, calibration version, ROS environment, commands, metric definitions, signal mapping, and plot generation code. A result without provenance is an observation, not an engineering baseline.
